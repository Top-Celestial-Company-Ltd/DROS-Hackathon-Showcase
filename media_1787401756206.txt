04 根因
為什麼不能直接寫一個 API Gateway？
因為這不是技術債，是法律設計的結果
戶政司
蒐集目的：戶政
衛福部
蒐集目的：社福
教育部
蒐集目的：教育
個資法第 5 條：公務機關只能在「執行法定職務的必要範圍內」利用個資，且必須與當初「蒐集的特定目的」相符。
戶政司當初為「戶政」蒐集的資料，社會局要拿來「審核補助」——那是另一個特定目的，法律上不能直接調。
所以解方不可能是「打通資料庫」。唯一的合法路徑是：讓民眾自己授權。

07 題目定義
六個信任要點，放到政府服務場景
Demo Day 評審會照這六點看你的作品
代表誰
Principal
Agent 代表這位民眾本人，還是代表
整個家戶？多人合併申辦時，其他家
人怎麼授權？
授權範圍
Authorization
「代查」和「代送件」是同一層授權
嗎？可以查所得，就可以查病歷嗎？
可呼叫工具
Tool / Action
Agent 能自動比對「部會 A 的憑證
」是否滿足「部會 B 的條件」嗎？
高風險攔截
Policy Gate
哪些動作必須本人親自確認？具法律
效力的簽署能不能交給 Agent？
稽核軌跡
Audit Log
申辦被駁回時，能否還原 Agent 當
時查了什麼、依據什麼填了什麼？
失效與撤銷
Expiry / Revocation
民眾隨時能撤銷委託嗎？撤銷後
Agent 是否立即停止？
不必做到產品級。重點是讓評審看懂：Agent 代表誰、被允許做什麼、高風險動作怎麼被擋、行為能不能追溯。

08 從哪裡下手
三個可以馬上動手的方向
不是標準答案——是讓你今天下午就能開始 vibe code 的起點
資格自動比對
最容易做出 Demo
讓 Agent 讀取 A 機關已核發的憑證，自動
判斷是否滿足 B 機關的申請條件，民眾不
必重填。
起手式：定義兩張假憑證的 JSON schema
，寫個 policy engine 做條件比對。
委託授權書
最貼近評分重點
設計一張「民眾委託 Agent 代辦」的可驗
證憑證：寫明代辦範圍、有效期限、哪些
動作需本人二次確認。
起手式：授權做成可撤銷 token，Demo 
時當場撤銷，讓 Agent 立刻停手。
主動式通知
最有故事性
反轉「申請制」——政府資料顯示你符合
資格時，Agent 主動提醒你、並備好申辦
草稿等你確認。
起手式：用育兒津貼場景，模擬「滿 2 歲
前 30 天」自動觸發跨部會轉換草稿。
也歡迎完全不走這三條——只要能回答那六個信任要點。

這題為什麼值得做
台灣已經把前兩段路鋪好了——MyData 解決取得，數位皮夾解決出示。你要做的是第三段：代理。
這不是假想場景。育兒津貼、長照、就學補助，每天都有人在四個網站之間來回填同一份資料。
個資法的限制不會消失。任何解方都必須建立在「民眾自己授權」之上——這正好是 AI Agent 信任設計的核心
命題。
把「你不申請就不給」，變成「你只要說一聲，Agent 幫你辦完」。
