五種憑證，三個類別
ISO 17442-3 第 5 章
類別 憑證 發證方向 回答什麼問題
實體類 QVI 憑證 GLEIF → 發證機構 這家機構可以發 vLEI 嗎？
實體類 法人憑證 (LE) QVI → 法人 這家公司是它宣稱的那家嗎？
授權類 發證授權憑證 (AUTH) 法人 → QVI 這家公司真的要求發這張嗎？
角色類 官方組織角色 (OOR) QVI → 自然人 這個人是登記在案的高階職務嗎？
角色類 業務參與角色 (ECR) 法人或 QVI → 自然人 這個人在哪個功能上代表公司？
授權類憑證的方向是「向上」的 —— 這是 QVI 無法替沒提出申請的公司發角色憑證的原因。

實務上最該分清楚的一組：OOR 與 ECR
選錯會導致法遵責任與營運彈性都放錯位置
OOR 官方組織角色
角色來源 公司登記、章程等公開文件
角色代碼 須符合 ISO 5009 官方角色清單
誰可發證 只有 QVI
典型用途 法律責任行為：簽署合約、
監理申報、法定代表
例子 董事長、總經理、董事
ECR 業務參與情境角色
角色來源 由法人自行定義
角色代碼 自由文字，法人自訂
誰可發證 法人可自行核發，或委由 QVI
典型用途 營運授權：日常授信操作、
供應鏈單據簽核
例子 貿易融資專員、
授權簽核人（限額 100 萬）
設計原則：法律責任用 OOR，營運授權用 ECR。多數應用真正需要的是 ECR。
122. vLEI 怎麼運作
--- Page 13 ---
底層的三件事
技術聽眾請留意；決策聽眾知道有這三層即可
KERI
金鑰事件收據基礎設施
• 識別碼由金鑰自我證明，不需註冊中心
• 預先輪替：今天就承諾好下一組金鑰的雜湊
• 私鑰外洩也奪不走識別碼
ACDC
可驗證鏈結資料容器
• 憑證格式，以 SAID 自我定址
• edge 區塊指向授權它的上一張憑證
• 改一個字元，整條鏈的雜湊立刻對不上
CESR
可組合事件串流表示法
• 把密碼學材料編成可讀的文字
• 同一段資料可在文字與二進位間無損轉換
• 可對文件的特定段落分別簽章
這三件事讓「可驗證」成為結構性質，而不是流程承諾。

一張 vLEI 憑證長什麼樣
每個 d 欄位都是內容的雜湊，改一個字就對不上
{
  "v": "ACDC10JSON0001c2_",
  "d": "EBc...",           憑證本身的 SAID
  "i": "EDe...",           簽發者 AID
  "ri": "EFg...",          憑證登錄簿
  "s": "ENPXp1vQ...",      Schema SAID
  "a": {                   屬性區
    "i": "EJk...",         持有人 AID
    "LEI": "8755001ELOZEL05BVX22"
  }, 
  "e": {                   邊 — 授權來源
    "auth": { "n": "ENo...",
              "s": "EKA5...", 
              "o": "I2I" } 
  }, 
  "r": { ...免責條款... }
}
SAID 自我定址
把 d 欄位換成等長的 # 之後計算雜湊，
再填回去。任何人都能重算驗證。
a — 屬性區
誰持有這張憑證、LEI 是多少、
姓名與角色。這是「內容」。
e — 邊區塊
指向授權這張憑證的上一張憑證。
這是「權限從哪裡來」。
r — 規則區
使用免責與簽發免責。
GLEIF 框架明文寫著：可驗證 ≠ 可信賴。
142. vLEI 怎麼運作
--- Page 15 ---
為什麼假冒不了：I2I 運算子
權限不是「宣稱」的，是「指向」的，而指標偽造不了
正常流程
1 法人 發出「授權 QVI-A 為某人核發董事長憑證」
2 QVI-A 持有這張授權，據以核發 OOR 憑證
3 驗證方 檢查：核發者 = 授權書的收受者 ✓
結果：驗證通過
攻擊嘗試
1 QVI-B 偷看到那張授權書的 SAID
2 QVI-B 自行核發 OOR 憑證，邊指向同一張授權
3 驗證方 檢查：核發者 ≠ 授權書的收受者 ✗
結果：驗證失敗，且不需要任何黑名單
I2I（Issuer-to-Issuee）規則：這張憑證的「核發者」必須就是它所指向那張授權憑證的「收受者」。

為什麼這樣設計 公司的 LEI 失效或身分被撤銷時，不該還留著一批仍然有效的授權簽核人在外面。

驗證方要注意 每一層都要查撤銷狀態，不能只查最末端那張憑證。
